## 1. 项目概述

### 1.1 要解决的问题

一位教学视频创作者，每次用手机拍摄 15 分钟以上的教学视频后，需要在剪映中手动添加关键帧缩放、图片叠加、字幕样式、转场等操作。剪辑风格相对固定，但每段视频的**语义触发点**不同（老师什么时候开始写公式？学生什么时候提问？）。

**目标**：发一段新视频 → AI 自动理解内容 → 按已有剪辑风格自动出片 → 得到一个完整的 mp4 成品。

### 1.2 问题的学术定义

底层核心问题是 **Video Temporal Grounding（VTG，视频时序定位）**：给定自然语言描述，在视频中定位对应的起止时间戳。加上多模态维度——既要懂声音（ASR + 说话人分离），又要懂画面（视觉理解），还要把两者对齐到时间轴。

### 1.3 与"AI 生成视频"的区别

| | AI 生成视频（MovieAgent 等） | 本项目 |
|---|---|---|
| **素材来源** | 从无到有生成 | 已有真实拍摄素材 |
| **核心任务** | 文生视频 / 图生视频 | 视频理解 + 时码定位 + 特效套用 |
| **AI 角色** | 创意生成（不可控） | 约束型理解+定位（可审计、可回退） |
| **所属领域** | Video Generation | Video Understanding / Editing |

## 3. 技术栈详解

### 3.1 FunClip — 中文语音识别 + 说话人分离

| 维度 | 说明 |
|---|---|
| **仓库** | `https://github.com/modelscope/FunClip` |
| **开发者** | 阿里巴巴通义语音实验室 / 达摩院 |
| **底层模型** | FunASR Paraformer（ASR）+ CAM++（说话人识别） |
| **许可证** | Apache 2.0（开源免费） |
| **运行位置** | 本地 CPU / GPU |
| **输入** | 视频文件（mp4 / mov / avi 等） |
| **输出** | `[{start: 0.0, end: 2.3, text: "今天我们来讲...", speaker: "老师"}, ...]` |
| **中文能力** | 业界最强中文 ASR 之一，原生支持中文口音、中英混合、方言 |
| **为什么选它** | 教学视频 = 中文为主 + 老师/学生交替说话。FunClip 的中文 ASR 能力 + 内置说话人分离，是这个场景的**最佳选择**。相比 WhisperX，FunClip 对中文识别率更高，且不需要 HuggingFace token |
| **局限** | 多人同时说话（重叠语音）会标错说话人；模型首次下载约 2GB；依赖 ModelScope 生态 |
| **替代方案** | WhisperX（多语言强但中文不如）、讯飞语音（商用需付费） |
| **在本项目的角色** | 阶段 1：把视频的音频转成带说话人标签的逐句文本 |

---

### 3.2 PySceneDetect — 场景/镜头切换检测

| 维度 | 说明 |
|---|---|
| **仓库** | `https://github.com/Breakthrough/PySceneDetect` |
| **开发者** | Brandon Castellano（社区维护） |
| **原理** | 逐帧计算像素差异（HSV 色彩空间），差异超过阈值判定为镜头切换 |
| **许可证** | BSD 3-Clause（开源免费） |
| **运行位置** | 本地 CPU |
| **输入** | 视频文件 |
| **输出** | `[{start: 0.0, end: 8.5}, {start: 8.5, end: 22.0}, ...]` |
| **检测模式** | ContentDetector（内容变化）、ThresholdDetector（黑场/淡入淡出）、AdaptiveDetector（自适应阈值） |
| **为什么选它** | 成熟稳定（GitHub 5k+ stars），命令行 + Python API 都有，教学视频固定机位居多、镜头切换明显，检测效果很好 |
| **局限** | 对渐变转场（叠化 crossfade）的边界不如深度学习模型（TransNetV2）精确；阈值需要根据视频风格微调 |
| **替代方案** | TransNetV2（深度学习，更准但需 GPU）、ffmpeg select filter（简单但不区分转场类型） |
| **在本项目的角色** | 阶段 1：把长视频切成语义段落，每段是"连续的同一个镜头" |

---

### 3.3 ffmpeg — 视频处理基础设施

| 维度 | 说明 |
|---|---|
| **下载** | `https://ffmpeg.org` |
| **是什么** | 命令行视频/音频处理工具，几乎所有视频软件（包括剪映、OBS、VLC）底层都依赖它 |
| **许可证** | LGPL / GPL |
| **运行位置** | 本地 CPU |
| **为什么选它** | 它是视频领域的"标准库"。FunClip 内部用它读视频、MoviePy 内部用它编解码、我们用它的场景覆盖：抽关键帧（`select` filter）、音频提取/转码、音频混合（`amix`）、最终格式转换 |
| **替代方案** | 没有——ffmpeg 是行业标准 |
| **在本项目的角色** | 辅助工具（不是主角）：</br>① 按场景时间戳抽取关键帧图片</br>② 提取/混合/调节音频轨</br>③ 被 MoviePy 内部调用做编解码 |

---

### 3.4 MoviePy — Python 视频编辑引擎

| 维度 | 说明 |
|---|---|
| **仓库** | `https://github.com/Zulko/moviepy` |
| **是什么** | Python 视频编辑库，提供面向对象的 API 操作视频：裁剪、缩放、叠加、转场、文字、特效 |
| **许可证** | MIT（开源免费） |
| **运行位置** | 本地 CPU |
| **核心 API** | `VideoFileClip`（加载视频）、`resize()`（缩放）、`CompositeVideoClip`（多轨合成）、`concatenate_videoclips`（拼接）、`fadein/out`（淡入淡出）、`set_audio`（替换音频） |
| **为什么选它** | 比裸写 ffmpeg `-filter_complex` 命令好维护 100 倍。几行 Python 就能表达"这个时间段的视频放大 1.15 倍 + 叠加一张图片并淡入 0.3 秒"。代码可读、可调试、可复用 |
| **局限** | 关键帧缓动函数（easing）不如专业剪辑软件丰富，贝塞尔曲线需手写；处理超长视频（>30 分钟）内存占用较高；社区版 v1.x 维护较慢（v2 在开发中） |
| **替代方案** | Remotion（React 做视频，效果最好但需 Node.js + 学习成本高）、直接 ffmpeg（功能全但代码难维护） |
| **在本项目的角色** | 阶段 3 执行引擎：读取 EDIT 操作 JSON → 逐段应用特效 → 渲染最终 mp4 |

---

### 3.5 qwen-vl-plus — 阿里通义视觉大模型

| 维度 | 说明 |
|---|---|
| **API 平台** | 阿里云百炼 DashScope（`https://dashscope.aliyun.com`） |
| **是什么** | 多模态大模型，能"看懂"图片内容，用中文描述画面中的人物、动作、环境、文字 |
| **运行位置** | 云端 API |
| **输入** | 一张 JPEG 图片（压缩后 100-200KB）+ 文字 prompt |
| **输出** | 结构化 JSON：`{labels: ["teacher_visible", "writing_on_board"], summary: "老师在白板上写数学公式"}` |
| **为什么选它** | 中文原生理解好（不像 GPT-4V 需要翻译层）、便宜（单张图几分钱）、有免费额度、对教学场景（黑板/PPT/人物/文字）识别准确 |
| **局限** | 需联网 + API key；有调用频率限制；单张图片静态理解，看不到视频动态（我们用双帧对比弥补） |
| **替代方案** | GPT-4V（更强但贵 10 倍、图片传海外）、ollama + qwen2.5-vl（本地免费但需 ≥8GB 显存） |
| **在本项目的角色** | 阶段 1：对每段视频的起止双帧分别理解，输出结构化语义标签 |

### 3.6 DeepSeek — 大语言模型

| 维度 | 说明 |
|---|---|
| **API 平台** | DeepSeek Platform（`https://platform.deepseek.com`） |
| **是什么** | 深度求索的大语言模型 API，OpenAI 兼容接口 |
| **运行位置** | 云端 API |
| **输入** | JSON 文本（风格参数 + 语义标签） |
| **输出** | 结构化风格规则 JSON |
| **为什么选它** | 极便宜（约 GPT-4 的 1/50）、中文能力强、支持超长上下文。在本项目中它**只用一次**：第一段把工程参数 + 语义标签对齐成风格规则 |
| **局限** | 输出格式偶有波动（需 retry + JSON Schema 约束）；高峰期响应较慢 |
| **替代方案** | qwen-plus（同样便宜）、GPT-4o（更聪明但贵 50 倍） |
| **在本项目的角色** | 阶段 2（仅第一段用）：一次性风格翻译。**第二段不再调用**，已被确定性 Python 标签匹配引擎替代 |

## 4. 数据流与处理规模

### 4.1 15 分钟视频（1080p，约 1.5GB）的处理链路

```
原始视频（1.5GB，本机）
        │
        ├─→ [本地] FunClip 只读音频流 (~150MB)
        │   → 输出：ASR 转写文本 + 说话人标签 (~50KB JSON)
        │   → 耗时：5-10 分钟（CPU）
        │
        ├─→ [本地] PySceneDetect 逐帧分析像素差异
        │   → 输出：场景起止时间戳列表 (~5KB CSV)
        │   → 耗时：~30 秒（CPU）
        │
        ├─→ [本地] ffmpeg 按场景抽关键帧（每段 2 张 × ~30 段）
        │   → 输出：60 张 JPEG 图片 (~200KB/张 = ~12MB)
        │   → 耗时：~20 秒（CPU）
        │
        ├─→ [云端] qwen-vl-plus 逐一描述每张图
        │   → 上传：60 张压缩图 (~6-12MB)
        │   → 输出：结构化标签 JSON (~2KB)
        │   → 耗时：2-3 分钟（网络+API）
        │
        ├─→ [本地] 标签匹配引擎
        │   → 输入：content_map.json + style_labels.json (~15KB)
        │   → 输出：edit_ops.json (~3KB)
        │   → 耗时：<1 秒
        │
        └─→ [本地] MoviePy 逐段渲染特效 + 合成
            → 输入：原始视频 + edit_ops.json + assets/
            → 输出：成片.mp4（与源文件同码率）
            → 耗时：10-20 分钟（CPU，取决于特效复杂度）
```

### 4.2 云端上传数据量分析

| 数据类型 | 单次大小 | 15 分钟视频的量 | 上传次数 |
|---|---|---|---|
| VLM 图片 | ~200KB/张 | 30-60 张 = 6-12MB | 每次出新片 |
| LLM prompt | ~10KB | 一次性 | 仅第一段 |
| 原片视频 | 0（不上传） | 0 | 永不 |

> **原片永远不出本机。** 云端只收到压缩小图 + JSON 文字。

### 4.3 总耗时估算（15 分钟视频）

| 环节 | 时间 | 可并行？ |
|---|---|---|
| FunClip ASR | 5-10 分钟 | 独立 |
| PySceneDetect | ~30 秒 | 独立 |
| 抽关键帧 | ~20 秒 | 依赖 PySceneDetect |
| VLM 描述（60 张图） | 2-3 分钟 | 依赖抽帧 |
| 标签匹配 | <1 秒 | 依赖 VLM |
| MoviePy 渲染 | 10-20 分钟 | 依赖匹配结果 |
| **总计** | **约 20-35 分钟** | — |

> 适合后台跑：放视频 → 喝杯咖啡 → 回来看成品。

## 5. 完整工作流

### 5.1 第一段：学习剪辑风格（一次性）

**你需要提供：**
- 一条你做好的成品教学视频（mp4，3-15 分钟）
- 你用的图片叠加素材（PNG：高亮框、卡片、Logo 等）
- ⭐（强烈推荐）剪映工程文件 `draft_content.json` + `materials/`

**AI 执行步骤：**

```
步骤 1 · 内容理解
  FunClip → ASR 转写 + 说话人分离
  PySceneDetect → 镜头切换检测
  ffmpeg → 每段抽起止双帧
  qwen-vl-plus → 双帧对比 + 结构化标签
  → 产出：ref/content_map.json

步骤 2 · 参数提取（如有工程文件）
  parse_draft.py → 解析 draft_content.json
  → 精确提取：关键帧数值、文字样式、转场类型、素材引用
  → 产出：ref/style_spec.json

步骤 3 · 风格翻译（DeepSeek，仅此一次）
  输入：style_spec.json + content_map.json
  输出：风格规则 JSON + 说明书
  → 产出：style_labels.json + skill_style.md

步骤 4 · 你审核
  确认风格规则正确 → 固化
  以后不再重做
```

### 5.2 第二段：每次出新片

**你只需要：**
- 把新拍的原始视频放到 `input/`
- 对 AI 说："按模板剪这段视频"

**AI 自动执行：**

```
步骤 1 · 内容理解（同第一段）
  FunClip + PySceneDetect + ffmpeg + qwen-vl-plus
  → 产出：content_map.json

步骤 2 · 标签匹配（确定性，不调 LLM）
  Python 匹配引擎：
  if rule.required_labels ⊆ segment.labels:
      → 命中规则 → 添加对应特效操作
  → 产出：edit_ops.json

步骤 3 · 渲染出片
  MoviePy 逐条执行 EDIT 操作
  → 关键帧缩放 + 图片叠加 + 字幕 + 转场 + 音频
  → 产出：output/成片.mp4
```

## 6. 关键设计决策

### 6.1 为什么最终不用 ffmpeg 裸命令，而用 MoviePy

| 操作 | ffmpeg 裸命令 | MoviePy |
|---|---|---|
| 缓慢缩放关键帧 | `zoompan=z='min(zoom+0.0015,1.15)':d=120` | `clip.resize(lambda t: 1.0 + 0.15 * t/4)` |
| 图片叠加 + 淡入 | 需手动算 overlay + fade 时序 | `CompositeVideoClip([base, overlay.fadein(0.3)])` |
| 多段拼接 + 转场 | 需先生成每段再 concat | `concatenate_videoclips([seg1, seg2], method="compose")` |
| 字幕烧录 | `drawtext` 参数繁琐，字体渲染差 | 可先用 Pillow 渲染再叠加，效果更好 |

> 结论：MoviePy 代码量少 80%，可维护性高 10 倍。裸 ffmpeg 只用于抽帧和音频处理。

### 6.2 为什么第二段不再调 LLM

原 B 方案让 DeepSeek 每次出新片都做"语义匹配"→ EDIT JSON。但本质上这是文本标签匹配——“writing_on_board”匹配"写公式"规则——不需要 LLM 的推理能力。v2 方案：

- VLM 输出**结构化标签**（不是自由文本）
- 匹配引擎用**Python 集合运算**：`required_labels ⊆ segment_labels`
- 结果：**免费、更快、100% 可复现**（同样的视频每次输出完全一致）

LLM 只保留第一段的一次性"风格翻译"——这才是需要推理能力的步骤。

### 6.3 为什么用双帧而非单帧

| 方案 | 能看到什么 | 看不到什么 |
|---|---|---|
| 单帧（段中间） | 白板上有公式 | 公式是刚写的还是一直在？ |
| **双帧（起 + 止）** | 帧1=空白板 + 帧2=有公式 | → 这段话是"写公式的过程" |

双帧对比让 VLM 能判断"这段发生了什么变化"，而不只是"这段画面是什么状态"。这对检测"写板书""切到 PPT""学生举手"等动作变化至关重要。

## 7. Skill 封装

### 7.1 什么是 Skill

在 WorkBuddy / Claude Code 中，Skill 是一份 `SKILL.md` 文件——AI 的操作手册。Skill 固化以下资产：

- 阶段 1 的分析 Pipeline 命令
- 阶段 2 的匹配引擎调用方式
- 阶段 3 的渲染参数和素材路径
- 剪辑风格规则（从第一段学会的）
- Prompt 模板（VLM 看画面用的、DeepSeek 风格翻译用的）

### 7.2 封装后怎么用

```
你：“剪这段教学视频，按我的模板”
         ↓
AI 读取 SKILL.md → 执行 Pipeline → 输出成片
```

你重写的只是那一句话 brief（"剪这段"），而不是整套方法论。

## 8. 限制与风险

| # | 风险 | 严重程度 | 缓解措施 |
|---|---|---|---|
| 1 | VLM 时间定位不精确（可能差几秒） | 🟡 中 | 双帧对比提升精度；保留人工微调 checkpoint |
| 2 | MoviePy 复杂缓动效果不如剪映 | 🟡 中 | 接受精度折损；长期可评估升级到 Remotion |
| 3 | 剪映工程文件结构随版本变 | 🟡 中 | 解析脚本按实际 dump 结构写，不靠猜字段名 |
| 4 | 说话人分离对重叠语音会标错 | 🟡 中 | 关键教学场景通常一人说话，重叠少 |
| 5 | 依赖云端 API（网络/限流/涨价） | 🟡 中 | 可切到套餐 A（ollama 本地模型）做 fallback |
| 6 | 语义标签误判（把"讲解"标成"写公式"） | 🟢 低 | VLM prompt 约束严格 + 风格规则写得具体 |
| 7 | 长视频 MoviePy 渲染慢 | 🟢 低 | 适合后台跑，不需要实时 |
| 8 | 如果没有工程文件 | 🟡 中 | 退回到"VLM 反推参数"模式，精度下降但可接受 |
